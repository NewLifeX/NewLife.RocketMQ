## 1. 整体架构

NewLife.RocketMQ 采用**分层清晰、职责单一、可扩展**的架构设计，纯 C# 实现，零外部依赖。

### 1.1 设计理念

- **纯托管实现**：完全使用 C# 实现，无需 Java、gRPC、Protobuf 第三方库
- **双协议支持**：同时支持 Remoting 协议（4.x/5.x Broker）和 gRPC 协议（5.x Proxy）
- **云厂商适配**：统一 ICloudProvider 接口，轻松接入各云服务商
- **高性能优化**：连接复用、对象池、VIP 通道、消息压缩等优化手段
- **可测试性**：40 个测试文件，546 个测试用例覆盖核心功能和边缘场景

## 6. 设计决策

| 决策点 | 选择 | 否决方案 | 理由 |
|--------|------|---------|------|
| Protobuf 编解码 | 手写字段编解码（基于 SpanWriter/SpanReader） | Google.Protobuf / protobuf-net | 零外部依赖，减少包体积和部署复杂度 |
| gRPC 通信 | HttpClient + HTTP/2 自研帧 | Grpc.Net.Client | 零外部依赖，仅需 netstandard2.1+ |
| 连接管理 | ConcurrentDictionary 连接池 | 第三方连接池库 | 简单高效，满足 Broker 少连接场景 |
| 消费者负载均衡 | 客户端平均分配 | 服务端 Rebalance | 兼容 4.x，5.x 服务端 Rebalance 需 Broker 配合 |
| 云厂商适配 | ICloudProvider 接口 + 策略模式 | 硬编码各厂商逻辑 | 易扩展，新增厂商只需实现接口 |
| 多目标框架 | net45/net461/netstandard2.0/netstandard2.1/net10.0 | 仅 netstandard2.0 | 覆盖企业遗留系统和最新平台；net10.0 承接 AOT 与裁剪场景 |
| 消息压缩 | 发送端 ZLIB 自动压缩 | 不压缩 / 手动压缩 | 大消息体自动优化带宽 |
| VIP 通道 | BrokerPort - 2 优先级连接 | 仅标准端口 | 提升高优先级消息性能 |
| 可插拔压缩接口 | IMessageCompressor + 扩展项目 | 直接引入外部 NuGet 依赖 | 主库保持零依赖；LZ4/ZSTD 按需安装扩展包 |
| AOT 兼容策略 | 仅 net10.0 开启 IsAotCompatible，库内序列化改走源生成访问器 + 元数据根 | 全目标框架引入 AOT 注解 / 运行时反射 | 老目标框架无裁剪概念，保持零注释成本；AOT 仅在需要的现代目标付代价 |
| AOT 对象体登记 | 公共 API MqAot.RegisterBodyType&lt;T&gt;()（DynamicallyAccessedMembers 泛型标注），老目标为空实现 | 要求消费方手写 DynamicDependency 元数据根 | 裁剪器只对静态可见的类型保留成员，库无法枚举消费方类型；一行登记把"静默发空对象"的踩坑点收敛为显式调用，且多目标工程共用同一份启动代码 |
| AOT 发布基线 | scripts/AotBaseline.cs 采集体积/启动/吞吐，CI 摘要与阈值判定 | 只做功能冒烟、不记录量化指标 | 裁剪环境下体积与启动开销易随依赖升级悄悄劣化；基线量化后可及时发现膨胀，阈值取得宽松只拦明显异常（win-x64：10.03 MB / 47 ms） |
| gRPC 资源上报 | 长连接 + 周期重建（GrpcTelemetrySession） | 一次性上报；第三方 gRPC 库的双向流 | 一次性上报后 Proxy 立即注销客户端；.NET 的 HttpClient 在请求体未结束时不上抛服务端响应，连接断开也无法从发送侧感知，故按周期重建连接重新上报设置即可自愈（含 Proxy 重启）；会话暴露 ConnectCount/ErrorCount 供长稳观测重建稳定性 |
| gRPC 截止时间 | 按调用声明 grpc-timeout（接收按挂起时间放宽，长连接不声明） | 不声明截止时间 | Proxy 依据截止时间计算剩余时间，缺失时 ReceiveMessage 直接空指针失败；长连接不能带截止时间以免被中断 |
| gRPC 消费重试 | 只消费原主题，由 Broker 把重试消息并回原主题的拉取响应 | 客户端订阅/轮询 %RETRY% 主题 | 5.x POP 模式失败消息写入 %RETRY%{group}_{topic}（v1）或 %RETRY%{group}+{topic}（v2），Broker 按 popFromRetryProbability（默认 20）概率并入原主题的 POP 响应；实测直接拉取重试主题始终返回空，故客户端无需感知重试主题 |
| gRPC 死信处理 | 客户端在投递次数达到上限时调用 ForwardToDeadLetterQueue | 依赖 Broker 自动转死信 | POP 模式下 Broker 不会自动转死信，未转发则消息在重试主题反复重投；GrpcPushConsumer.MaxDeliveryAttempts 默认 16，Consumer 提供 ForwardToDeadLetterQueueViaGrpcAsync 与 GetGrpcDlqTopic |
| gRPC 死信消费语义 | 死信处理必须「拉取 → 处理 → 确认」一次完成，工具 scripts/DlqTool.cs 重投后立即确认 | 把死信队列当只读列表浏览 | 实测：死信消息被拉取即推进 POP 位点，未确认的消息在不可见时间到期后会被 Broker 移入 %RETRY%{group}_%DLQ%{group}，既读不到也无法用同一消费组重投，因此只支持一次性处理而不提供只读列表模式 |
| gRPC FIFO 顺序消费 | 客户端串行处理（GrpcPushConsumer.Orderly），Broker 按 message_group 保证投递顺序 | 依靠并发消费后自行排序 | FIFO 消息的顺序由 Broker 保证，但客户端并发处理会打乱完成顺序（实测并发 20 时完全乱序、串行时严格有序）；顺序消费牺牲吞吐换取确定性，多队列并行场景由调用方按队列拆分消费者 |
| gRPC 事务消息 | 显式 EndTransaction 提交或回滚；主题类型须为 TRANSACTION；Broker 未收到决议时按超时回滚 | 依赖客户端回查处理 | 5.x 的事务回查通过 Telemetry 双向流下发 VerifyMessageCommand，客户端当前为只写流无法应答（见已知限制），因此半消息不会自动提交，超时后被 Broker 回滚；此外 Proxy 在发送时以主题名作为生产者组，事务消息的生产者组语义弱于 Remoting |
| gRPC 不可见时间下限 | 库内收敛到 10 秒并告警 | 原样提交调用方设定值 | Broker 校验 ILLEGAL_INVISIBLE_TIME min is 10000，小于 10 秒的取值直接报错；库内统一收敛避免调用方踩坑 |
| 本地 Broker 内存参数 | 启动脚本为 Broker 单独加 -XX:MaxDirectMemorySize=1g | 沿用默认（与堆上限相同） | Broker 的 POP 拉取大量占用直接内存，默认上限随 -Xmx（512m），长时间压测后 OutOfMemoryError 导致 POP 失败，表现为重试停滞、消费进度不再推进 |
| gRPC ACL 鉴权 | authorization 头携带 HMAC-SHA1 签名，摘要输出十六进制 | 输出 Base64 | Proxy 侧只解析 Credential/SignedHeaders/Signature 三段，并先对 Signature 做 hex→base64 再与本地 HMAC 结果比对；直接输出 Base64 会签名不匹配而被判无权限（实测非管理员与错误密钥返回 PERMISSION_DENIED，管理员可正常收发） |
| gRPC 延迟消息 | 延迟等级按 Broker 默认 messageDelayLevel 换算为投递时间戳 | 沿用 Remoting 的延迟等级属性 | Proxy 不识别 Remoting 的 DELAY 属性，且主题类型非 DELAY 时会以 MESSAGE_PROPERTY_CONFLICT_WITH_TYPE 拒绝，故换算为 deliveryTimestamp 并置于 DELAY 类型主题 |
| gRPC 发送属性 | 过滤 TAGS/KEYS/DELAY 等系统保留键后再下发 properties | 原样透传 Message.Properties | Remoting 把 Tags/Keys 也写进 Properties 随请求头下发，但 Proxy 视这些键为系统保留（ILLEGAL_MESSAGE_PROPERTY_KEY）而整条拒绝 |
| gRPC 优雅下线 | Stop 时显式调用 notifyClientTermination，失败仅告警不阻断停止 | 依赖 Telemetry 长连接断开让 Proxy 超时注销 | Proxy 侧的客户端注册带会话超时，不显式通知时从本地停止到 Proxy 注销存在窗口期，期间 POP 分配仍指向已停止的消费者，消息要等超时后才被重新投递；实测通知后 Proxy 立即 clear handle 并移除 channel，Stop 开销约 11ms |
| gRPC 单向发送 | PublishOneway 在 gRPC 模式改为异步发送模拟：不等待回执、失败仅记录日志、返回合成 SendOK | 抛 NotSupportedException | gRPC 没有单向语义，Proxy 下用"普通发送后本地丢弃结果"保调用方代码不变；与真正单向仍有差异（多一次完整 RPC 往返），单次失败仅日志体现 |
| 多 RID 测试覆盖 | 单元测试与 AOT 冒烟按 RID 矩阵运行：原生 runner 逐一发布运行；LA64 用 QEMU 用户态仿真 + 龙芯 SDK（宿主跑 x64 服务端，LA64 客户端共享网络直连） | 仅在 linux-x64 验证 | NativeAOT 官方不支持跨 OS 编译，必须原生 runner；LA64 无官方 runner 与 runtime pack，QEMU 仿真可跑通 JIT 冒烟与全量单测；新平台先观察期（continue-on-error），连续全绿后转阻断 |

## 7. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 各云厂商 5.x gRPC 接入未验证 | 阿里云 Serverless / 华为云 5.x / 腾讯云可能不兼容 | 客户端 gRPC 链路已本机 Proxy 实测打通（发送/接收/确认/推送消费），待实际环境逐步验证 |
| 手写 Protobuf 编解码与官方标准偏差 | 极端数据格式可能解析失败 | 30+ 测试覆盖核心编解码场景，并有对照官方 proto 的黄金字节用例，持续补充边界用例 |
| RocketMQ 新版本协议变更 | 新增 RequestCode / Header 字段 | MQVersion 枚举已扩展到 V5.9.9 + HIGHER_VERSION，跟进社区更新 |
| 阿里云公网版 BrokerName 不匹配 | 消费者偏移匹配可能失败 | 已用容错代码处理，不影响核心消费流程 |
| 连接泄漏或超时 | 长时间运行可能资源不足 | 心跳保活 30s + 连接池管理 + Dispose 释放 |
| ACL 2.0 Broker 版本兼容 | 请求头在旧版本 Broker 可能被拒绝 | 新字段加入前检测 Broker 版本；默认不加入该字段，向后兼容 |
| NativeAOT 下反射序列化失效 | 模型成员被裁剪后序列化为空对象，消费组注册等链路失败 | net10.0 启用源生成成员访问器 + DynamicDependency 元数据根；AotSmoke 冒烟覆盖编解码/序列化/压缩/端到端/gRPC 链路 |
| NativeAOT 下消费方自定义类型（POCO 消息体）被裁剪 | 未登记类型的公开属性被移除，对象体静默序列化为 `{}`，收方拿到空对象且无任何报错 | 提供 MqAot.RegisterBodyType&lt;T&gt;() 一行登记（net10.0 带 DynamicallyAccessedMembers 保留语义）；AotPackageSmoke 以四种组合（未登记/仅访问器/仅元数据根/API 登记）固化实测差异，文档在 Readme 的 NativeAOT 章节给出接入指引 |
| 只写 Telemetry 流无法响应服务端指令 | Proxy 下发的校验消息、打印线程栈等命令不会被应答（不影响收发主链路） | 记录为已知限制；如需应答需改为可读双向流，受限于 .NET HttpClient 的请求体-响应并发行为 |
| Proxy 重启后的短暂失败窗口 | 连接重建并重新上报设置期间（默认不超过 60 秒 + 注册生效 1.5 秒），接收请求可能返回服务端“订阅信息为空”的错误 | 会话自动重建连接并重新上报，实测 Proxy 杀掉再拉起后数秒内恢复收发；调用方按常规重试即可（消费循环本身持续重试） |
| Broker 直接内存耗尽后 POP 静默失败 | 失败消息不再重投、消费进度停滞，客户端侧仅表现为长时间收不到消息 | 本地启动脚本为 Broker 加 -XX:MaxDirectMemorySize=1g；生产环境按消息体量与并发评估该参数；现象与 Broker 日志 OutOfMemoryError: direct buffer memory 对应 |
| Broker 清库后 Proxy 的无效拉取 | Proxy 订阅的内部主题 DefaultHeartBeatSyncerTopic 不存在时会持续拉取，刷满 Broker 日志并抢占拉取线程，表现为消费类请求大面积超时；且 Proxy 首次查不到路由后会一直沿用空路由 | 启动脚本与 CI 在启动 Proxy 前自动创建该主题；Broker 重启后还需重启 Proxy（或等待其路由缓存刷新），否则无效拉取不会因主题补齐而停止；本地排障时若见大量 the topic ... not exist 日志，先补齐内部主题、再重启 Proxy 后复测 |
| Proxy 开启 ACL 后无法启动 | 报 create system broadcast topic DefaultHeartBeatSyncerTopic failed，Proxy 起不来 | ACL 打开后 Proxy 自身的请求也需鉴权，须先以管理员凭据预建该内部主题再启动 Proxy；Proxy 侧配置项是 enableACL 与 enableAclRpcHookForClusterMode（写成 aclEnable 会被忽略，表现为鉴权完全不生效） |
| 非 x64 平台兼容性回归 | 帧编解码、压缩、序列化在 ARM/龙芯/边缘平台上出现平台相关缺陷，用户侧才暴露 | CI 多 RID 矩阵：win-x64/linux-x64/linux-arm64/LA64 必选覆盖（LA64 经 QEMU，其 AOT 冒烟不作强制要求、失败不阻断），win-arm64/osx 双架构/musl/边缘 RID 观察期；AOT 冒烟与单元测试双层验证 |

## 附录 E：gRPC（Proxy）能力边界

Proxy 5.3.1 的 `GrpcMessagingApplication` 只暴露 11 个业务 RPC（经 jar 类清单核实），客户端已 100% 覆盖，没有未实现的客户端能力，也不存在可用 gRPC 实现的管理接口：

| Proxy RPC | 客户端方法 | 说明 |
|-----------|-----------|------|
| queryRoute | QueryRouteAsync | 路由查询 |
| heartbeat | HeartbeatAsync | 客户端注册与保活 |
| sendMessage | SendMessageAsync / SendTransactionMessageAsync | 普通（含 FIFO、延迟、优先级）与事务半消息 |
| queryAssignment | QueryAssignmentAsync | 队列分配 |
| receiveMessage | ReceiveMessageAsync | POP 拉取（长轮询） |
| ackMessage | AckMessageAsync | 确认 |
| changeInvisibleDuration | ChangeInvisibleDurationAsync | 延长不可见时间（延迟重投） |
| forwardMessageToDeadLetterQueue | ForwardToDeadLetterQueueAsync | 转发死信 |
| endTransaction | EndTransactionAsync | 提交/回滚事务消息 |
| notifyClientTermination | NotifyClientTerminationAsync | 优雅下线通知 |
| telemetry | TelemetryAsync | 双向流：设置上报与服务端指令 |

由此可确定两条边界：

- **管理类操作无法走 gRPC**：建/删主题、订阅组管理、消息查询、消费统计等均无对应 RPC，只能直连 Broker（Remoting）。库内 9 个管理方法已前置校验并抛出带指引的 NotSupportedException，避免调用方撞上空引用异常
- **能力对齐依据**：后续 Proxy 版本若新增 RPC，可用同样的类清单方式比对，判断是否需要补齐客户端实现
